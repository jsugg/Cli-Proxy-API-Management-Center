# Quota summaries

The quota page has two separate data sources: manually fetched current snapshots and optional server-recorded history. No new dependency, account or inference routing rule is introduced. Provider subscription counts are unchanged.

Each row is an **unweighted mean of remaining percentages**, grouped by provider, limit ID and actual window duration. It is not pooled tokens or spendable capacity. Short, weekly, monthly and model-specific limits remain independent. Plans have no invented multipliers. Different accounts can have different reset times; the next reset is the earliest future reset among contributing observations, not the entire pool's reset.

Limit rows follow the windows reported by successfully loaded accounts for each provider; null or inapplicable slots do not create rows. Until any account for that provider loads successfully, the usual Unknown placeholder rows remain; reported windows with unusable or stale values still display Unknown.

Coverage is contributing credential observations divided by all enabled credentials for that provider, across every page and tab. Aliases for the same provider account cannot reliably be deduplicated with the current identity contract; this is a credential summary, not a unique-person count. Duplicate cache identities count once. Disabled credentials do not count. Unloaded, failed, refreshing, explicitly stale, future-dated, older-than-15-minute, invalid percentage, missing-duration and missing/expired-reset observations contribute no value. Zero contributors display Unknown, never zero or full. The minute clock expires old samples without extra provider calls. Refresh remains the existing explicit per-card/current-page action.

Codex now carries a browser receipt timestamp, like Claude. Neither is provider-certified observation time. Summaries require the current connection's successfully loaded credential list. Cache invalidation and request-generation guards are unchanged.

Quota account labels prefer the normalized safe `email` metadata from the credential scanner/registry, never `account` or `account_type`, which may contain secrets. A label is the clean email alone, not a technical filename or an added credential ID. Only when metadata is unavailable does the display helper recognize the matching `claude-<number>-<email>.json` or `codex-<number>-<email>.json` filename convention. It does not guess arbitrary hash/plan suffixes, strip prefixes from metadata or rename files. Non-email names remain names; malformed email-like filename fallbacks are hidden rather than presented as guessed addresses.

Default masks retain the full domain and one clear ellipsis. Locals of at least nine characters normally show four leading and three trailing characters, such as `jupiter.gamma.two@example.test` becoming `jupi…two@example.test`. Shorter locals reveal less, always hiding at least one character. If the same provider has distinct emails with colliding masks, a pure collection-local resolver expands only the necessary visible prefix or uses another partial mask, without ever revealing a whole local part or appending an ID. For example, `jupiter.alpha.one` and `jupiter.beta.one` become `jupiter.a…one` and `jupiter.b…one`. There is no persisted alias registry. Exact duplicate addresses and irreducible very-short collisions remain identical; explicit Show emails or existing plan context must distinguish those cases.

The same scoped labels feed quota cards, timeline rows/tooltips, history selectors, accessible names and confirmation labels. Show emails reveals the clean full email and stays in page memory only. Credit-dialog presentation follows reveal/hide reactively while its mutation context remains fixed; generic reset confirmation text uses the label selected when it opens. Action notification names deliberately remain masked even when Show emails is enabled, so a late asynchronous response cannot restore an earlier revealed label after Hide. Full domains remain visible even when masked, so this is not an anonymity or secret-storage boundary. It does not redact network payloads or secure browser storage. Cache keys, filenames, auth indexes, account-user operation keys and API mutation targets remain exact, including Devin/plugin cache identity rules. Arbitrary non-email filenames may still contain personal information.

## Server-recorded history

The optional quota-history companion adds schema v1 under the existing authenticated `/v8/management/quota-history` prefix. Its canonical contract is `CLIProxyAPI/docs/jnet-quota-history.md` in the companion repository. The native inference server is unchanged. The frontend first checks `/quota-history/capabilities`, then reads `/quota-history` through the existing management API client and the same admin key. Missing capabilities or unsupported schemas show an unavailable state. Other failures show an explicit retryable error, never an empty/full quota claim.

History reads refresh every 60 seconds, without browser provider probes. The companion samples centrally every 300 seconds and persists observations for up to 30 days. No history exists before collection starts. New installations show the actual first samples immediately; rates unlock only after sufficient observations accumulate. The older timeline still projects reset **schedules**, not recorded utilization. Token logs are never converted into subscription history.

Every provider tab checks the collector capabilities. Supported tabs scope history reads to that provider; the All tab reads all collected providers. A provider-scoped panel disappears when that provider is unsupported. Time ranges are one hour by default, or six/24 hours. Pages share an immutable range/filter/limit and follow the exact `cursor` returned by the service. Each page is bounded by the server capability and 2,000 observations; a view loads at most five pages, or 10,000 observations. Partial results are labelled and cannot produce forecasts. Load more retrieves another bounded page; automatic refresh preserves the number of pages already requested. Narrow the range when the page ceiling is reached. Repeated cursors, malformed/oversized responses and out-of-range samples fail closed.

Tracks are independent provider/opaque-account/limit/actual-period identities. The server's `series_id` includes plan, period and reset boundaries. Provider-quality IDs can deduplicate credential aliases. Credential-quality IDs cannot identify unique people; Codex currently uses this conservative identity and displays the caveat. Nothing sums subscriptions into token capacity. Existing credential filenames can label a matching native auth index, with emails masked by default; unmatched accounts use shortened opaque IDs. Native auth indexes are never displayed.

Solid segments and dots are real recorded observations. Unknown rows, missing observations, usage decreases and series/reset changes break recorded lines. Unknown data is not zero. Account-wide `limit_id=unknown` observations invalidate every limit for that account. A limit-scoped unknown observation with no period invalidates every duration track for that same account/limit. Duration tracks keep separate measurements but share observed period-change boundaries, so an obsolete duration cannot forecast and returning to a prior duration cannot bridge the intervening change. The companion records failed probes, backoff, disappearing windows and enumeration failures as unknown observations so later successful polls cannot erase those gaps. Collection failure status also disables forecasts, even before the collector becomes stale.

### Conservative estimates

- Use only the most recent contiguous suffix within 60 minutes. Require at least three distinct successful timestamps spanning at least 15 minutes, a latest sample no older than 10 minutes, and no adjacent gap longer than 15 minutes.
- Never cross account, provider, limit, series, period, reset or decreasing-utilization boundaries. Identical timestamp duplicates collapse; conflicting duplicate readings become an unknown gap.
- Observed burn is the first-to-last utilization change divided by elapsed hours, in **percentage points per hour**, not tokens, money or a provider-wide pool rate. Show contiguous sample count/span, latest age and usable/total observation coverage. Flat observations show no measurable rate and unknown exhaustion.
- Dashed forecasts explicitly assume the recent rate stays constant. Start at the latest actual observation and stop at exhaustion, the next reported reset, or a horizon no more than one hour ahead. Never invent repeated resets, refills or sawtooths. Exhaustion remains unknown when it falls outside that bounded current-window projection.
- Stale/failed collectors, unknown windows, insufficient samples and incomplete pagination disable projections. These rules are eligibility checks, not statistical confidence guarantees.

The browser neither persists nor reconstructs history. It holds a bounded server snapshot in memory. Connection-pinned authentication, abort controllers, request ownership and quota-cache generations suppress late responses and clear displayed history across logout, connection changes and provider/range switches. Read-only requests have 15-second deadlines, no retry storm and no additional key entry.

## Verification fixture

The development-only `/#/__preview/quota-tiers` route renders real summaries, history charts, timelines and quota cards with synthetic data. Three same-domain synthetic accounts per provider exercise recognizable masks, scoped collisions, metadata precedence and clean reveal consistently across views. Card fixtures have no native auth index, preventing provider probes; history uses separate synthetic indexes for label lookup only. History fixtures cover ready, first-sample, collecting, unsupported, partial, stale, gaps, flat and collection-failure states. They require no management key or backend and never mount the network history loader. Production builds remove this route. Browser checks against these fixtures do not validate live provider responses.

## Burn rate page

The separate `/burn-rate` page reads one four-day history snapshot for every provider advertised by the collector. It follows up to 30 bounded pages automatically, then refreshes incrementally with a 15-minute overlap. Incomplete incremental reads and ranges extending before the previously loaded start fall back to a full bounded load. It never probes providers or persists history. The Quota-page history panel keeps its existing conservative one-hour forecast rules.

Each provider row groups independent limits by limit ID and actual period. Long windows, the default, are at least one day; short windows are less than one day. The four freshest groups with the lowest current mean remaining percentages are shown. Colors follow lexical limit identity among all groups in the selected window family, including hidden or stale groups, cycling through the four-color palette. These are equal-account percentage averages, not pooled tokens or spendable capacity. Account IDs deduplicate credential aliases only when the collector has provider-quality identity; credential-quality counts can include aliases.

Recorded lines use absolute five-minute epoch boundaries over the past four days, plus a live endpoint. An account contributes its latest measurable observation in the preceding 15 minutes only while its reset is still in the future. Accounts with any row in that interval are expected; if any expected account has a latest unknown row, the pooled cell is a gap. Accounts without a row in the interval are not expected. Missing values leave gaps. Account window changes flag pooled boundaries and split recorded paths. The table exposes the same grid without relying on hover or color.

This page estimates each account's rate from its current reset window using `sameHistorySeries`, the same actual period and non-decreasing cumulative utilization. The baseline is the last 24 hours or the period length, whichever is shorter, within that window. Unknown polls leave recorded gaps but do not discard comparable cumulative readings on either side. A series, reset, period or usage reversal ends the baseline, including window identities carried by unknown rows. At least three distinct measurable observations must span 5% of the period, clamped to 15 minutes through two hours. The latest reading must be no older than the greater of ten minutes and three collector poll intervals. Sufficient flat samples measure a rate of zero and count as rated.

Rates are percentage points per day. Each rated account projects linearly from its latest observation to its own reported reset, clamping the remaining percentage at zero. The summary averages rates across all contributing accounts, counting unrated accounts as zero, and averages each contributing account's remaining percentage at its own reset. Coverage says how many contributors support a rate. Unrated contributors are held flat and explicitly labelled. The earliest contributing reset and earliest exhaustion within the drawn window are shown separately. Exhaustion must fall between that account's latest observation and its reset, and no later than the earliest pooled reset or chart horizon. An already empty account exhausts at its latest observation; past exhaustion reads "used up". The countdown ring shows elapsed time in the earliest current window.

The chart shows four days back and three days forward. The pooled dashed line starts at the solid live endpoint and ends at the first contributing reset. That endpoint, the now label and the dot use the same mean, projecting each account from its own latest observation. Known refills appear as dashed reset markers. Only the earliest reset has a hollow dot at a post-refill pooled value; later resets have no pooled value because earlier-reset accounts' usage is unknown. There is no usage line after a reset and no invented repeated reset schedule. A reset beyond the displayed horizon is labelled with an arrow. Past reset markers deduplicate bounded reset-time drift. Stale or failed collectors, failed refreshes, partial pages and capped loads disable all projections. Freshness also expires on the shared minute clock. These assumptions are not statistical confidence guarantees.

The development-only `/#/__preview/burn-rate` route uses synthetic Claude, Codex and xAI observations, independent weekly/Fable limits, staggered reset times, a recorded refill, partial rate coverage and explicit collecting/stale/failure states. It mounts only the injectable view and never the network loader. Production builds omit this preview.
